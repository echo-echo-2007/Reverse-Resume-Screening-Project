> 4. **措辞调整**：`pending` 由「待初筛」改为「待处理」（= 已通过自动初筛、等 HR 看）；HR 自己拒的（`reject_stage='manual'`）仍在「已拒绝」里可见。
> 5. 第 8 节的问题 4（初筛预览 `dry_run`）随之作废——既然不再手动触发，也就没有「预览一次初筛」的场景。

## 1. 现状盘点

### 1.1 后端已有能力（都能直接用）

| 接口 | 用途 | 备注 |
|---|---|---|
| `GET /api/jobs?mine=1` | 本企业全部职位（含非 published） | 非 published 只有本企业能看 |
| `POST /api/jobs` | 新建职位 | 强制 `published`；校验见 3.4 |

| `POST /api/jobs/:id/screen` | 一键初筛（只处理 `pending`） | 返回 `total/passed/rejected/results[]` |

### 1.2 缺的能力

| 缺什么 | 影响 | 处理方式 |

| 企业信息编辑 | 公司名、行业注册后改不了 | V1 不做 |

## 3. 页面一：HR 工作台 `/hr`

### 3.1 布局

```
┌──────────────────────────────────────────────────────────────┐
│ 工作台                                    [+ 发布新职位]      │
│ 星辰科技有限公司 · 互联网                                      │
├──────────────────────────────────────────────────────────────┤
│ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐      │
│ │在招职位│ │待初筛  │ │初筛通过│ │面试中  │ │已录用  │      │
│ │   4    │ │   5    │ │   3    │ │   2    │ │   1    │      │
│ └────────┘ └────────┘ └────────┘ └────────┘ └────────┘      │
├──────────────────────────────────────────────────────────────┤
│ 我的职位                                                      │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 前端工程师            [在招]      本科 · 2 年 · 上海       │ │
│ │ 15K-25K   5 条投递（2 待初筛）        11-13 发布   [管理] │ │
│ └──────────────────────────────────────────────────────────┘ │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 产品经理              [在招]      不限 · 不限 · 不限       │ │
│ │ 面议      0 条投递                    11-12 发布   [管理] │ │
│ └──────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 概览指标

| 卡片 | 口径 | 点击行为 |
|---|---|---|
| 在招职位 | 本企业 `jobs` 条数 | 无（就在本页） |
| 待初筛 | `pending` 的投递数 | 跳 `/hr/applications?status=pending` |
| 初筛通过 | `screened` | 同上，带 `status=screened` |
| 面试中 | `interview` | 同上 |
| 已录用 | `hired` | 同上 |

数据来自 `GET /api/hr/overview`（一次请求）。**注意**：卡片只做「数字 + 跳转」，不做趋势图。

**为什么不能前端自己拼**：现有接口只能按职位拉投递，5 个职位就是 5 次请求，职位多了会明显变慢，而且统计口径容易和投递管理页对不上。

### 3.3 职位列表

每条卡片点击进「投递管理」并自动选中该职位（`/hr/applications?job_id=xx`），右侧「编辑」进 `/hr/jobs/:id/edit`。

| 展示项 | 数据来源 | 说明 |
|---|---|---|
| 职位名称 | `title` | 粗体，过长省略 |
| 状态标签 | `status` | V1 都是 `published`，显示「在招」；非 published 显示灰色「已下线」 |
| 硬条件串 | `min_education_level` / `min_experience_months` / `city_name` | 形如「本科 · 2 年 · 上海」，不限显示「不限」 |
| 薪资 | `salary_min/max` | 复用 `formatSalary`，橙色；都为 0 显示「面议」 |
| 投递数 | 新接口带回来 | 形如「5 条投递（2 待初筛）」，0 条时只显示「还没有投递」 |
| 发布时间 | `created_at` | 复用 `formatRelativeDay`（今天发布 / 昨天发布 / 11-13 发布） |

### 3.4 职位表单（新建 / 编辑共用）

| # | 字段（数据库列） | 界面标签 | 控件 | 必填 | 校验规则 | 库限制 |
|---|---|---|---|---|---|---|
| 1 | `title` | 职位名称 | 单行输入 | ✅ | 非空，≤ 128 字 | varchar(128) |
| 2 | `department` | 招聘部门 | 单行输入 | ❌ | ≤ 64 字 | varchar(64) |
| 3 | `salary_min` + `salary_max` | 薪资范围 | 两个数字输入，单位 **K** | ❌ | `0 ≤ min ≤ max ≤ 999`；都填 0 视为面议 | unsigned int |
| 4 | `min_education_level` | 最低学历 | 下拉（不限/高中/大专/本科/硕士/博士 → 0–5） | ✅ | 0–5 整数，默认「不限」= 0 | unsigned tinyint |
| 5 | `min_experience_months` | 最低经验 | 数字输入（单位 **年**，可填 0.5） | ❌ | 0–60；提交时 ×12 存月 | unsigned int |
| 6 | `city_code` + `city_name` | 工作城市 | 下拉（8 城 + 不限） | ❌ | 选中同时写 code 与 name；不限则两者都空 | char(6) / varchar(64) |
| 7 | `description` | 职位描述 | 多行文本（8 行） | ❌ | 无硬限制 | mediumtext |
| 8 | `requirements` | 任职要求 | 多行文本（6 行） | ❌ | 无硬限制 | mediumtext |

口径说明（和求职者端保持一致，避免两边算错）：

- **薪资**：界面单位是 K（填 15 → 存 15000）。`salary_min = salary_max = 0` 表示面议，列表显示「面议」。
- **经验**：界面单位是年（填 2 → 存 24 个月），与 `resumes.work_months` 同口径，初筛直接比大小。
- **学历**：界面「不限」= 0，与 `min_education_level` 默认值一致；求职者端最低档是 1（高中及以下），所以 0 永远不会拦人。

### 3.5 交互细节

| 场景 | 行为 |
|---|---|
| 新建成功（201） | 提示「职位已发布」，回工作台并高亮新职位；**不提供草稿**，创建即可见 |
| 编辑成功（200） | 提示「已保存」；若改了硬条件，另提示一句「只影响之后新投递的初筛，已处理的不会重算」 |
| 薪资区间填反（min > max） | 前端拦住，字段下红字；后端也会校验（双保险） |
| 编辑时有人删了职位 / 越权 | 404 / 403 → 顶部红条显示后端文案，表单内容不丢 |
| 离开时有未保存修改 | 与「我的简历」一致，拦一下（复用同一套 `beforeunload` + 站内链接拦截） |

### 4.2 顶部筛选

| 控件 | 行为 |
|---|---|
| 职位下拉 | 「全部职位」+ 本企业职位列表（复用 `SelectMenu`）；**选中具体职位后**「开始初筛」才可用 |

| 开始初筛 | 弹确认框：「将处理该职位 N 条待初筛投递，已处理的不会重算」→ 调接口 → 结果见 4.7 |

筛选项写进 URL query（`?job_id=&status=`），刷新不丢，也方便从工作台卡片点进来直接定位。

### 4.3 列表字段

| 列 | 数据来源 | 说明 |
|---|---|---|
| 姓名 | `resumes.full_name` | 点整行打开简历抽屉 |
| 学历 | `highest_education_level` | `EDU_LABEL` 映射 |
| 经验 | `work_months` | `formatMonths`（0 显示「应届/无经验」） |
| 期望城市 | `expected_city_name` | 空显示「不限」 |
| 投递时间 | `applied_at` | `formatDateTimeShort`（`MM-DD HH:mm`） |
| 状态 | `status` | 复用 `STATUS_LABEL` / `STATUS_STYLE` 标签 |
| 拒绝原因 | `reject_stage` + `reject_reason` + `reject_note` | 仅 `rejected` 显示，规则同求职者端 |
| 操作 | — | 见 4.5 按钮矩阵 |

「全部职位」视图下多一列「应聘职位」（`jobs.title`），单职位视图下隐藏该列（已在标题里）。

### 4.4 简历抽屉

点行打开右侧抽屉（不是新页面，避免来回跳）：

- **联系信息**：姓名、手机号（可复制）、邮箱（可复制）——HR 的核心诉求，直接展示
- **求职信息**：期望城市、最高学历、学校、毕业年份、工作年限（年）
- **正文**：工作经历、自我评价（保留换行）
- **对照硬条件**：抽屉顶部一行「岗位要求：本科 · 2 年 · 上海」，逐项标绿/标灰，便于人工复核
- 底部固定操作条：与 4.5 相同的状态按钮

### 4.5 状态流转与按钮矩阵

| 当前状态 | 可点按钮 | 调用 |
|---|---|---|
| `pending` 待初筛 | 初筛通过 / 拒绝 | `PATCH status = screened / rejected` |
| `screened` 初筛通过 | 安排面试 / 拒绝 | `PATCH status = interview / rejected` |
| `interview` 面试中 | 录用 / 拒绝 | `PATCH status = hired / rejected` |
| `hired` 已录用 | 无（终态） | — |
| `rejected` 已拒绝 | 无（终态） | — |

- 按钮必须**按状态机给**，不要给一个「改状态」下拉让 HR 自己选，非法流转后端会 400。
- 点非「拒绝」的按钮：直接调接口，成功后该行状态就地更新（不整页刷新）。
- 点「拒绝」：弹窗填原因（见 4.6）。

### 4.6 拒绝弹窗

```
┌──────────────────────────────┐
│ 拒绝这份投递                  │
│ 赵通过 · 前端工程师            │
│                              │
│ 拒绝原因 *                    │
│ ○ 学历不符  ○ 经验不足        │
│ ○ 城市不符  ● 其他            │
│                              │
│ 备注（选「其他」时必填）        │
│ ┌──────────────────────────┐ │
│ │                          │ │
│ └──────────────────────────┘ │
│                     [取消] [确认拒绝]│
└──────────────────────────────┘
```

- 原因四选一：`education` / `experience` / `city` / `other`，默认选中与「当前不满足项」对应的那个（例如经验不够就预选「经验不足」）。
- 备注 ≤ 255 字（库限制），选「其他」时必填，其他情况选填。
- 提交成功后：该行变「已拒绝」+ 原因行；求职者端「我的投递」同步可见（同一个 `PATCH` 接口）。
- 后端会把 `reject_stage` 写成 `manual`，界面上区分「系统初筛」和「HR 操作」。

### 4.7 初筛的交互与反馈

1. 只有选了具体职位，「开始初筛」才可点；未选时 hover 提示「先选一个职位」。
2. 点击 → 确认框：「将对《前端工程师》的 N 条待初筛投递执行初筛，已处理的不会重算」。
3. 执行中按钮转圈并禁用，防重复点击。
4. 返回 `{ total, passed, rejected, results[] }`：
   - `total = 0` → 「没有待初筛的投递」（不报错）
   - 否则顶部绿色条：「初筛完成：通过 3 条，拒绝 2 条」+「看明细」展开结果列表（姓名 + 结果 + 原因）
5. 完成后刷新当前列表，统计行同步更新。

**已知限制**（写进页面底部小字）：初筛只看学历、经验、城市三个硬条件；任意一边城市为空时跳过城市判断。

## 5. 接口清单

### 5.1 新增：`GET /api/hr/overview`

HR 权限：`requireAuth` + `requireRole('hr')`，`company_id` 从 token 取。

返回：

```json
{
  "company": { "id": 1, "name": "星辰科技有限公司", "industry": "互联网" },
  "jobs": { "total": 4, "published": 4 },
  "applications": { "total": 12, "pending": 5, "screened": 3, "interview": 2, "hired": 1, "rejected": 1 }
}
```

实现要点：`jobs.count` 一次 + `applications.groupBy({ by: ['status'], where: { jobs: { company_id } } })` 一次，共 2 次查询。

### 5.2 新增：`GET /api/hr/applications?job_id=&status=`

```json
{
  "total": 12,
  "applications": [
    {
      "id": 8,
      "status": "pending",
      "applied_at": "2026-11-20T06:32:00.000Z",
      "jobs": { "id": 5, "title": "前端工程师", "city_name": "上海" },
      "resumes": {
        "full_name": "赵通过",
        "highest_education_level": 4,
        "work_months": 36,
        "expected_city_name": "上海"
      }
    }
  ]
}
```

- 列表**不返回** `work_experience` / `self_evaluation` / 联系方式，抽屉打开时再按 5.3 拉，省流量。
- `job_id` 可选；不传即「全部职位」。
- 排序固定 `applied_at desc`。
- V1 不分页，返回全部（数据量小）；前端如需限制，加 `limit` 兜底。

### 5.3 可选：`GET /api/applications/:id`

抽屉用。返回完整简历 + 所属职位硬条件，顺带写 `hr_viewed_at = now()`（字段已有，一直没用）。

> 如果第 8 节问题 3 选「不做已读」，这条可以先不做，抽屉直接用 5.2 的数据 + 再调一次 `GET /api/jobs/:id/applications` 兜底——但那是绕路，建议还是加。

### 5.4 可选：`POST /api/jobs/:id/screen?dry_run=1`

只算不写，返回「如果现在初筛，会通过 X 条、拒绝 Y 条」。给「初筛预览」用，避免 HR 手抖把一批人拒了。

### 5.5 明确不做

- 职位下线 / 删除 / 恢复
- 批量改状态（多选后一次性处理）
- 投递撤回、面试安排、Offer
- 企业信息编辑
- AI 评分、技能匹配

## 6. 数据口径与已知坑

| 坑 | 说明 |
|---|---|
| 薪资单位 | 库里是**元**，界面填 **K**，转换只在前端做（×1000 / ÷1000）。0-0 表示面议，不要显示成「0K-0K」 |
| 经验单位 | 库里 `min_experience_months` 是**月**，界面填**年**（可 0.5），×12 存库；和简历的 `work_months` 同一口径 |
| 学历档位 | 职位侧 0 = 不限，简历侧 1–5；比较时 `0` 永远通过，不要写成 `>= 1` 之外的特殊判断 |
| 初筛不回溯 | 只处理 `pending`；改职位硬条件后，已 `screened` / `rejected` 的不会重算 |
| 城市判断 | 职位或简历任意一边城市为空 → 跳过这一项，不当作不匹配 |
| 时区 | 库里 `applied_at` 存 UTC，接口带 `Z` 返回，前端直接用 `new Date()` 本地 getter（`formatDateTimeShort` 已处理） |
| 越权 | 所有 HR 接口都不接受前端传 `company_id`，一律从 token 取；否则改个参数就能看别家数据 |
| 状态机 | 前端按钮严格按 4.5 给，不要提供「任意状态」的入口 |

## 8. 待定问题（需要你拍板）

**问题 1：投递管理的入口形态？**
- A（推荐）**单页 + 顶部职位下拉**：「全部职位」是默认视图，选具体职位后才出现「开始初筛」。一页看全，少跳转。
- B 先选职位再进名单：从工作台卡片点进去，页面标题固定是某职位。层级清楚，但看「今天有哪些新投递」要多点两次。

**问题 2：概览统计要不要单独加接口？**
- A（推荐）加 `GET /api/hr/overview`，2 次查询拿到全部数字。
- B 不加，前端逐职位拉投递自己算。职位少时没感觉，职位一多就慢，且口径容易和列表页不一致。

**问题 3：简历「已读」状态做不做？**
- A（推荐）做，打开抽屉即写 `hr_viewed_at`（字段现成），列表给未读加个小圆点。
- B 本期不做，省一个接口。

**问题 4：初筛要不要「预览（dry_run）」？**
- A 做：先看「会通过 3 条、拒绝 2 条」再确认执行，防手抖。
- B（推荐）不做：确认弹窗已经写了「处理 N 条」，V1 从简。等你说要再加。

**问题 5：拒绝弹窗的默认原因？**
- A（推荐）按当前不满足的硬条件预选（经验不够 → 预选「经验不足」），HR 少点一下。
- B 不预选，强制 HR 自己选，避免「默认值被顺手提交」。

**问题 6：职位编辑后要不要提示「初筛不会重算」？**
- A（推荐）改过硬条件的保存后提示一句。
- B 不提示，写进页面底部小字说明即可。

## 附：与求职者端的对应关系

| 求职者看到 | HR 侧对应动作 | 接口 |
|---|---|---|
| 投递后状态「待初筛」 | 出现在投递管理，状态 `pending` | `POST /api/jobs/:id/apply` |
| 状态变「初筛通过」 | 点「开始初筛」或人工「初筛通过」 | `POST /screen` / `PATCH status` |
| 状态变「面试中」 | 点「安排面试」 | `PATCH status = interview` |
| 状态变「已录用」 | 点「录用」 | `PATCH status = hired` |
| 看到「已拒绝 · 系统初筛 · 学历不符」 | 初筛自动写入 `reject_stage = sql` | `POST /screen` |
| 看到「已拒绝 · HR 操作 · 其他（备注）」 | 拒绝弹窗填写 | `PATCH status = rejected` |
